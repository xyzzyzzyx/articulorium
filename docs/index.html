A linked data repository for libraries and archives, built from small services.

Articulorium is an open source W3C Linked Data Platform 1.0 server with Fedora Commons compatible extensions. It stores content in OCFL, protects it with Web Access Control, and adds the structures a digital library needs: collections, PCDM objects, IIIF manifests and COAR Notify inboxes.

Run it locally View the source on GitHub

Apache License 2.0. Java 25, Spring Boot 4.1, Spring Cloud 2025.1, Angular.

Who it is for

Repository and digital library teams

Organise material into communities, sub-communities and collections, build books, newspapers, journals and other objects from PCDM topologies, and publish them through a public discovery site with a IIIF viewer.

Developers and integrators

Work against open specifications instead of a private API: LDP for resources, Memento style versions, WebAC for permissions, IIIF Presentation 3.0, OAI-PMH 2.0 and Linked Data Notifications. Each service publishes an OpenAPI description.

Operators

Run the whole stack with Docker Compose, or the platform alone as one jar. Services register with Consul, exchange events over Kafka, and expose health, metrics and readiness probes through Spring Boot Actuator.

What it does

Each capability below is documented in the repository, and each links to the section that describes it. Paths are shown as they appear on a local stack behind the gateway.

  • Linked Data Platform and Fedora compatible APIs

    RDF sources, basic, direct and indirect containers and files, with GET, HEAD, OPTIONS, POST, PUT, PATCH (SPARQL Update) and DELETE. Responses come as Turtle, JSON-LD, N-Triples, RDF/XML, RDF/JSON or N3, with strong ETags and Prefer headers. Fedora style endpoints add versions, fixity, search and archival groups.

    Using the LDP API

    /platform/

  • Versioning and fixity

    Every file write is a new version, and any resource can be snapshotted on request. Versions are listed as JSON or as a Memento TimeMap. A fixity check hashes the stored bytes again and validates the OCFL object that holds them.

    Fedora API extensions

    <resource>/fcr:versions <file>/fcr:fixity

  • OCFL storage

    Content and versions are written as Oxford Common File Layout objects, one per resource, on an S3 compatible object store (MinIO in the local stack) or the file system. An archival group keeps a container and everything inside it in a single object, versioned as a unit.

    Storage (OCFL)

    articulorium.storage.type

  • Web Access Control

    Every request is checked against WebAC authorizations for read, append, write and control, set on a resource or inherited from an ancestor. People sign in with OpenID Connect (Keycloak by default); Consul tokens and a trusted proxy header are supported too. Search results leave out what the caller may not read.

    Access control (WebAC)

    <resource>/fcr:acl

  • PCDM structures

    Topologies describe kinds of digital object as trees of PCDM collections and objects. Book, Newspaper, Journal, Postcards, Manuscript and Audiovisual recording are built in, and custom ones are stored in the repository. Building a topology creates the containers, ordering and file slots for you.

    Topologies (PCDM structures)

    /topology/topologies

  • IIIF export

    A PCDM object exports as a IIIF Presentation 3.0 Manifest with a canvas per leaf object for its image, audio or video. Collections and communities export as IIIF Collections. The discovery layer presents them in Mirador.

    IIIF

    /transform/iiif/<path>

  • COAR Notify

    Every container has a Linked Data Notifications inbox and an outbox. Incoming notifications are validated against COAR Notify and Activity Streams 2.0 before they are stored, and the user interface sends the common patterns such as review and endorsement requests.

    Notifications (COAR Notify)

    <container>/fcr:inbox <container>/fcr:outbox

  • Search and indexing

    The platform answers attribute searches itself. Changes also flow to a Solr collection through pluggable transformers, and to a SPARQL 1.1 store (QLever) with one named graph per resource. A server rendered discovery site searches the index with facets and filters.

    Discovery layer, Transformations

    /platform/fcr:search /discover/

  • OAI-PMH and harvesting

    An OAI-PMH 2.0 data provider exposes records as Dublin Core, with communities and collections as sets. In the other direction, the harvest service brings in records from OAI-PMH providers, DSpace 7 and later, Fedora Commons 6 and VIVO.

    OAI-PMH, Harvesting

    /oai?verb=Identify

Also included

  • Academic profiles described with the VIVO ontology, with a validating editor.
  • A user interface and discovery site shipped in 12 languages, including right to left Arabic.
  • An optional AI agent that suggests topologies, metadata and topics. It never writes to the repository; people review its suggestions and apply what they keep.
  • A GraalVM native image profile for every service.

How the services fit together

One LDP server holds the data. Everything else is a separate Spring Boot service that either talks to it over LDP or reacts to its change events, so a deployment can leave out the parts it does not need.

  1. Entry point

    • gateway Spring Cloud Gateway. Routes the user interface, the discovery site, the APIs and the identity provider, and serves one Swagger UI for all services.

  2. Services that read and write through LDP

    • service Serves the Angular user interface and its support API.
    • discovery discovery-ui The public search and presentation site.
    • topology PCDM topologies and the resources built from them.
    • transform IIIF exports and search documents.
    • oai OAI-PMH 2.0 data provider.
    • harvest Harvests other repositories into the platform.
    • ai Optional agent that makes suggestions for review.

  3. The repository

    • platform The LDP server: RDF sources, containers, files, versions, fixity, search and access control.

  4. Services that follow changes

    • transform Turns each changed resource into a search document.
    • index Keeps a Solr collection in sync.
    • triplestore Mirrors every resource into a SPARQL 1.1 store.

  5. Where things are kept

    • PostgreSQL Resource metadata, access control lists and notifications. Other databases can be configured.
    • OCFL Content and versions, on S3 compatible storage or disk.
    • Solr and QLever The search index and the SPARQL store.
    • Consul, Kafka and Keycloak Service discovery and configuration, the event bus, and sign-in.

The README lists every module, including the shared libraries for Activity Streams 2.0, agents and internationalization.

Run it locally

You need Docker with Compose v2. To build without Docker you need Java 25 and Maven 3.9.

  1. Get the source

    git clone https://github.com/xyzzyzzyx/articulorium.git
cd articulorium

  2. Start the stack

    docker compose up --build

    The first start builds every service and downloads the AI agent's model, which is several gigabytes.

  3. Open the user interface

    Browse to http://localhost:8000/. Sign in as curator with the password curator. This and the other demo accounts exist for local use only.

    /ui/
    User interface
    /discover/
    Public discovery site
    /platform/
    LDP root
    /swagger-ui.html
    API reference for all services

  4. Create your first resources

    P=http://localhost:8000/platform

curl -i -X POST $P/ -H 'Slug: books' -H 'Content-Type: text/turtle' \
     --data '<> <http://purl.org/dc/terms/title> "Books" .'

curl -i -X POST $P/books -H 'Slug: cover.png' -H 'Content-Type: image/png' \
     --data-binary @cover.png

The README covers every local address, running the platform alone and building and testing.
